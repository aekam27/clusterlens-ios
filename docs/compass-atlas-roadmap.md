# ClusterLens: comprehensive MongoDB client roadmap

## Product target and evidence

The target is a full MongoDB client for iPhone/iPad with Compass-level usefulness and ease of use, plus explicitly scoped Atlas capabilities. Quick lookup is one workflow within that target, not a reason to exclude administration, editing, analysis, or bulk data workflows. Mobile adaptation should make the complete workflow practical through progressive disclosure, task-focused screens, keyboard support, resumable drafts, and bounded background work; it must not silently remove correctness or write safeguards.

This historical matrix compares the initial cursor-pagination checkpoint with the official pages linked below, checked during this iteration. **Implemented** means present in local code, not proven on iOS or a live cluster. **Partial** means a subset exists. **Planned** means absent from the current app. **Gated** means work additionally depends on platform/protocol feasibility, runtime validation, credentials, explicit permissions, or service/tier availability. It is not a claim of full Compass/Atlas parity or an exhaustive inventory of every Atlas product.

## Phased delivery and acceptance gates

These are proposed dependency-based milestones, not deadline promises. “Done” requires the complete user workflow plus error/permission handling and appropriate runtime evidence.

1. **Validate the existing foundation.** Preserve the safety guards, typed values/confirmed writes, and cursor paging. Complete Xcode builds, XCTest, device/UI/accessibility, TLS/getMore/killCursors/failover and memory validation. Finish a compatibility matrix for server versions, topology and auth. No current host-only test is a substitute for this gate.
2. **Complete everyday query ergonomics.** Structured filter/projection/ordered sort + JSON mode, filtered cursor paging, named queries, drafts and visible connection context. Acceptance: reopen a saved query, change a parameter, page exact BSON results, inspect/copy chosen fields, cancel/exit/reconnect without stale results or secret leakage. On iPad, use a navigator/result/editor split; on phone, preserve context across focused screens.
3. **Complete data editing and movement.** Type-aware document editing/diffs, database/collection management, bounded bulk jobs and streamed import/export. Acceptance: exact BSON types survive file/editor/database round trips; large jobs remain memory-bounded; partial failures are explicit; writes cannot change target between review and dispatch; unknown outcomes are never blindly retried.
4. **Complete analysis and administration inside the database.** Visual aggregation with saved pipelines and stage previews, index workflows, explain, schema sampling/validators and deeper diagnostics. Acceptance: demonstrate the workflow from slow query to explanation and a reviewed index change; show sampling uncertainty; preserve writes/privilege boundaries for output stages and admin actions.
5. **Complete advanced connectivity and workspace capabilities.** Implement the validated auth/private-access matrix, session/resource policies and advanced-command/shell strategy. Acceptance includes background/foreground, network changes, cursor/session expiry, revoked auth and multi-connection isolation under repeated use. Cap memory/connections from measurements rather than simply shrinking every workflow to an unusable preview.
6. **Add Atlas cloud capabilities through a separate authorized integration.** Inventory API endpoints and roles; implement read-only account/project/deployment visibility and monitoring, then separately confirmed administrative actions. Backups, restore, scaling, access and billing-related operations require their own resource/cost/permission review. Data Explorer workflow parity and Atlas cloud-administration parity must be tracked separately.
7. **Close the remaining catalogue deliberately.** Keep a release-versioned matrix of supported/partial/gated workflows, including advanced Compass features and other Atlas services. A parity claim needs reproducible acceptance runs for that stated version/scope, not a checkbox based on marketing names.

## Immediate engineering recommendation

After the pager's runtime gate, the highest-value next implementation is the structured query bar connected to this cursor lifecycle, together with ordered compound-sort representation and named saved queries. This builds a coherent query workflow instead of leaving the pager and JSON workbench disconnected. Exact numeric values, bounded memory, explicit cursor semantics and immutable write confirmation remain mandatory across later features.

The broader goal does not authorize connecting a real database, creating Atlas credentials, changing cloud resources, installing heavy toolchains, accepting new service terms or publishing code. Those actions remain outside the current local-build task.
